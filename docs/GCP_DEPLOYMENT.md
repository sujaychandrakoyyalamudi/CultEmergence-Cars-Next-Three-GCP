# Google Cloud deployment for cultemergence.com

## Recommended topology

Use Cloud Run behind a **global external Application Load Balancer** through a serverless network endpoint group. The load balancer provides the stable global IP, Google-managed certificate, HTTP-to-HTTPS redirect, Cloud Armor attachment and optional CDN. This avoids relying on Cloud Run’s limited direct domain mapping path and gives one edge for both `cultemergence.com` and `www.cultemergence.com`.

## Prerequisites

- A Google Cloud project with billing enabled.
- Owner-controlled access to the `cultemergence.com` registrar/DNS.
- `gcloud`, Docker and Terraform installed locally or in an approved CI runner.
- A committed `package-lock.json` generated by `npm install` and reviewed in CI.
- An identity permitted to enable services and create Artifact Registry, Cloud Run, Compute, DNS and IAM resources.
- A protected production workflow using Workload Identity Federation rather than service-account keys.

## 1. Verify locally

```bash
npm install
npm run check
npx playwright install --with-deps chromium
npm run test:e2e

docker build -t cultemergence-cars:local .
docker run --rm -p 8080:8080 cultemergence-cars:local
curl --fail http://127.0.0.1:8080/api/health
```

Commit `package-lock.json` after the first reviewed dependency resolution.

## 2. Authenticate and select a project

```bash
gcloud auth application-default login
gcloud config set project YOUR_PROJECT_ID
gcloud config set run/region us-central1
```

For CI, configure GitHub OIDC → Google Workload Identity Federation and provide only the provider and deployment service-account identifiers as protected environment secrets. Do not create a JSON service-account key.

## 3. Bootstrap protected Terraform state

Choose a globally unique bucket name:

```bash
cp infra/bootstrap/terraform.tfvars.example infra/bootstrap/terraform.tfvars
terraform -chdir=infra/bootstrap init
terraform -chdir=infra/bootstrap plan \
  -var='project_id=YOUR_PROJECT_ID' \
  -var='state_bucket_name=YOUR_UNIQUE_TF_STATE_BUCKET'
terraform -chdir=infra/bootstrap apply \
  -var='project_id=YOUR_PROJECT_ID' \
  -var='state_bucket_name=YOUR_UNIQUE_TF_STATE_BUCKET'
```

The bootstrap bucket has uniform access, public-access prevention, versioning and no force-destroy. Restrict bucket IAM to the Terraform deployment principal and emergency administrators.

Copy `infra/terraform/backend.tf.example` to `backend.tf`, replace the bucket value, and use a distinct prefix for each environment.

## 4. Create the initial Artifact Registry repository

The workload Terraform creates the repository and runtime stack, but the Cloud Run service needs an image reference. Use a two-step first deployment:

1. Temporarily create the repository with a targeted plan, or create it once with `gcloud artifacts repositories create cultemergence --repository-format=docker --location=us-central1`.
2. Build and push the image.
3. Apply the complete Terraform plan with that immutable image.

A pure-Terraform alternative is to publish a small approved bootstrap image first and replace it with the application digest in the same reviewed rollout.

## 5. Build and push an immutable image

```bash
TAG="$(git rev-parse --short=12 HEAD)"
gcloud builds submit . \
  --config=cloudbuild.yaml \
  --substitutions=_REGION=us-central1,_REPOSITORY=cultemergence,_IMAGE=cars-web,_TAG="$TAG"
```

Resolve the digest:

```bash
IMAGE="us-central1-docker.pkg.dev/YOUR_PROJECT_ID/cultemergence/cars-web:$TAG"
DIGEST="$(gcloud artifacts docker images describe "$IMAGE" --format='value(image_summary.digest)')"
IMMUTABLE_IMAGE="us-central1-docker.pkg.dev/YOUR_PROJECT_ID/cultemergence/cars-web@$DIGEST"
echo "$IMMUTABLE_IMAGE"
```

Use the digest, not `latest`, in production Terraform.

## 6. Plan infrastructure

```bash
cp infra/terraform/terraform.tfvars.example infra/terraform/terraform.tfvars
terraform -chdir=infra/terraform init
terraform -chdir=infra/terraform fmt -check -recursive
terraform -chdir=infra/terraform validate
terraform -chdir=infra/terraform plan \
  -var='project_id=YOUR_PROJECT_ID' \
  -var="container_image=$IMMUTABLE_IMAGE" \
  -var='domain=cultemergence.com' \
  -var='manage_dns=false' \
  -out=cultemergence.tfplan
```

Review the plan for:

- one Cloud Run service listening on 8080;
- public invoker only through load-balancer ingress;
- global IP, serverless NEG, backend service, URL maps and HTTP redirect;
- managed certificate for apex and `www`;
- Cloud Armor rate limiting;
- no unexpected IAM role or destructive change.

Apply only after explicit owner approval:

```bash
terraform -chdir=infra/terraform apply cultemergence.tfplan
```

## 7. Configure DNS

### DNS managed outside Google Cloud

Leave `manage_dns=false`. Obtain the IP:

```bash
terraform -chdir=infra/terraform output -raw load_balancer_ip
```

Create:

```text
cultemergence.com.      A      LOAD_BALANCER_IP
www.cultemergence.com.  A      LOAD_BALANCER_IP
```

Remove conflicting A/AAAA/CNAME records. Use a low TTL during cutover and raise it after verification.

### Cloud DNS managed by Terraform

Set `manage_dns=true`, apply, then delegate the registrar to the nameservers shown by:

```bash
terraform -chdir=infra/terraform output -json dns_name_servers
```

DNSSEC is enabled on the zone. Complete registrar-side DS configuration only after following Google Cloud DNSSEC guidance; do not improvise DS values.

## 8. Verify TLS and routing

The managed certificate becomes active only after public DNS points both requested names to the load balancer. Check:

```bash
gcloud compute ssl-certificates describe cultemergence-managed-cert --global
curl -I http://cultemergence.com
curl -I https://cultemergence.com
curl --fail https://cultemergence.com/api/health
curl -I https://www.cultemergence.com
```

Expected behavior:

- HTTP redirects to HTTPS.
- TLS certificate covers apex and `www`.
- home, comparison, at least one car route, sitemap and health return success.
- a missing route returns the styled 404.
- security headers appear on HTML responses.

## 9. Production workflow

`.github/workflows/deploy.yml` is manual and bound to a protected `production` environment. It authenticates through WIF, submits Cloud Build with the Git SHA as image tag, and updates the existing Cloud Run service to that immutable tag. For stricter infrastructure ownership, replace the final `gcloud run services update` command with a reviewed Terraform plan/apply that changes only `container_image`.

## Rollback

List revisions and images:

```bash
gcloud run revisions list --service=cultemergence-cars --region=us-central1
gcloud artifacts docker images list us-central1-docker.pkg.dev/YOUR_PROJECT_ID/cultemergence/cars-web --include-tags
```

Roll back by setting the service/Terraform `container_image` to a previously verified digest. Do not rebuild old source under a new dependency graph and call it the same release.

## Cost and scaling defaults

Development defaults use `min_instances=0` and `max_instances=10`. Production can set one minimum instance if cold-start latency warrants the cost. The application has no database, queue or object store; the principal costs are Cloud Run, load balancing, Cloud Armor logging, build minutes, Artifact Registry storage and DNS if enabled. Configure billing budgets and alerts outside this module for the project’s actual spending threshold.
